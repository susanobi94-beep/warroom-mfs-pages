Aperçu du Projet

Contexte opérationnel et problématique résolue

🔴

Problème

Dans un réseau de plus de 500 agents Mobile Money répartis sur plusieurs routes, les ruptures de float (stock épuisé) se produisent silencieusement. Les équipes terrain n'ont aucun outil pour détecter un agent en difficulté avant que le client soit refusé. Le suivi était 100% manuel (fichiers Excel envoyés par WhatsApp), entraînant des retards de plusieurs heures et une perte de revenus.

✅

Solution

Système automatisé en Python qui :

  • Collecte les fichiers de transactions CSV déposés par le système bancaire
  • Réconcilie chaque agent avec sa cible OOS (niveau de rupture) depuis le fichier OOS1.xlsx
  • Calcule le taux de rupture, le gap financier et les jours de couverture stock
  • Alerte l'équipe WhatsApp en temps réel avec un diagnostic complet
  • Publie tout sur un dashboard Streamlit hébergé sur Hugging Face Spaces

Architecture Technique

Pipeline de traitement de bout en bout

3

4

Upload vers Hugging Face Spaces (filtrage horaire prioritaires en journée)
5

Génère le rapport WhatsApp : ruptures, routes critiques, top HVC, prédictions
6
whatsapp_sender.py
Envoie le message via Playwright (WhatsApp Web) dans le groupe cible

🗂️ Flux de Données

  • Entrée : CSV transactions par agent (MSISDN)
  • Référentiel : OOS1.xlsx (cibles, routes, segments, priorité)
  • Sortie : reconciliation.csv (529+ lignes)
  • Historique : balance_history.csv, cycle_history.csv, pos_oos_history.csv

⚙️ Orchestration

  • auto_sync.py : boucle infinie, surveille le dossier source
  • Batch size : push HF tous les 500 fichiers traités
  • Idle timeout : rapport WhatsApp 30s après le dernier fichier
  • Start : start_auto_sync.bat

☁️ Hébergement

  • Dashboard : Hugging Face Spaces (Streamlit)
  • Push : API huggingface_hub (pas de git brut)
  • Filtrage : reconciliation 331 prioritaires (05h–17h Cameroun)
  • Complet : tous agents envoyés en soirée/nuit

Modules du Système

Détail de chaque composant Python

📥

transaction_processor.py

Collecte et normalisation des données de transaction.

  • Lit les fichiers Transactions_MSISDN.csv déposés automatiquement
  • Extrait : Date, Balance, Nom (From/To selon le numéro détecté)
  • Double encodage (UTF-8 puis Latin-1 en fallback)
  • Consolidation incrémentale dans summary.xlsx via openpyxl
  • Gestion des doublons : mise à jour de la ligne existante si MSISDN déjà présent
PythonopenpyxlCSV
🔗

reconciliation_global.py

Cœur analytique — réconciliation et calcul des KPIs.

  • Jointure : summary.xlsx ↔ OOS1.xlsx sur MSISDN (inner join)
  • OOS Rename Map : normalise les variantes de colonnes (priorité/priorite/PRIORITE…)
  • Dédoublonnage : groupby MSISDN → mean() pour numériques, first() pour catégoriels
  • Valeur Calculée : Balance − Montants OOS (gap négatif = rupture)
  • Jours de Stock : Balance ÷ Day_Target (avec fallback sur Montants OOS)
  • Historique global : history.csv (taux rupture, POS count par jour)
  • Historique routes : history_routes.csv (par route et par jour)
  • Cache mtime : skip si les fichiers sources n'ont pas changé
PandasopenpyxlKPIs
📊

dashboard.py (WAR ROOM)

Interface Streamlit dark-mode "War Room" pour visualisation temps réel.

  • Design : OLED #080C14, typographie Space Grotesk / Inter, accents or
  • Filtres sidebar : Site, Sous-Zone, Route, Segment, Priorité
  • KPIs : Taux OOS, Taux Rupture, Injection nécessaire, Jours de Stock
  • War Room Classifier : agents classés CRITICAL / WARNING / STABLE
  • Onglets : Vue Globale, Détail Agents, Récidivistes, Nouveaux POS, Historique, GPS
  • Récidivistes : agents en rupture sur plusieurs cycles + export CSV
  • Daily Trends : balance_history.csv → graphique Jours de Stock sur la durée
  • Moteur prédictif : affichage predictive_plan.csv (temps estimé avant rupture)
StreamlitPlotlyAltair

hf_sync_manager.py

Synchronisation intelligente vers Hugging Face Spaces.

  • Mode journée (05h–17h Cameroun) : upload uniquement les 331 agents prioritaires (priorite=oui)
  • Mode soir/nuit : upload complet (tous agents)
  • Upload folder : OOS1.xlsx, summary.xlsx, history.csv, history_routes.csv…
  • Upload API séparé : reconciliation.csv/.xlsx avec filtrage mémoire (pas toucher le fichier disque)
  • Redémarrage Space : optionnel via include_code=True (dashboard.py, requirements.txt…)
  • Rate limit : détection 429 avec message explicite
huggingface_hubHfApiBytesIO
⚡

predictive_engine.py

Moteur prédictif : estimation du temps avant rupture totale.

  • Méthode : snapshots JSON entre cycles → vitesse de consommation (FCFA/heure)
  • Seuil : alerte si autonomie < 4 heures
  • Sorties : Heure_Rupture_Estimee, Heures_Restantes, Vitesse_H
  • Fichier : predictive_plan.csv mis à jour à chaque cycle
  • Correction : UTC → UTC+1 (fuseau Cameroun) pour affichage correct
PandasJSONTime Series
🤖

agent_mfs.py (MFSAgent)

Générateur de rapport WhatsApp automatique à chaque cycle.

  • Analyse globale : POS totaux, taux rupture, tendance intra-journée (Δ par rapport au cycle précédent)
  • Par cluster (Site) : taux rupture avec flèches tendance ↑↓
  • Par segment : HVC / Standard (🔴🟡🟢 selon seuils)
  • Par route : taux, nombre POS en rupture, tendance cycle-à-cycle
  • Zones critiques : routes > 25% avec recommandation action terrain
  • Top 5 HVC : High-Value Customers en rupture avec gap FCFA
  • Prédictions : alertes <4h intégrées depuis PredictiveEngine
  • Archivage : cycle_history.csv (permanent) + pos_oos_history.csv
PandasJSONAnalytics

Système WhatsApp

Deux composants : envoi automatique + bot interactif sur le même groupe

📤

whatsapp_sender.py — Envoi Automatique

Pilote WhatsApp Web via Playwright (Chromium headless persistant) pour envoyer le rapport du MFSAgent après chaque cycle de traitement.

  • Session persistante : dossier wa_session/ sauvegarde le profil Chromium ; le QR code n'est scanné qu'une seule fois
  • First-time setup : python whatsapp_sender.py --setup ouvre le navigateur pour scan
  • Test : python whatsapp_sender.py --test envoie un message de test
  • Recherche groupe : multi-sélecteurs avec fallback (span[title], text-is, premier résultat de liste)
  • Saisie multi-lignes : Shift+Enter pour les sauts de ligne dans WhatsApp
  • Envoi : tentative bouton span[data-icon='send'] puis fallback Enter
  • Screenshot : capture wa_last_sent.png après envoi pour confirmation visuelle
  • Anti-détection : --disable-blink-features=AutomationControlled + user-agent réaliste
🎧

whatsapp_bot.py — Bot Interactif

Écoute en continu le groupe WhatsApp et répond automatiquement aux commandes des équipes terrain.

  • Polling : lecture du dernier message entrant toutes les 5 secondes
  • Anti-boucle : ignore les messages commençant par 🤖 (ses propres réponses)
  • Parsing multi-lignes : gère les messages de groupe (nom expéditeur + commande sur la même bulle)
  • Stratégies de lecture : 5 sélecteurs CSS + fallback div[role='row'] pour résister aux changements WhatsApp
  • Réponse rapide : < 2 secondes entre réception et envoi de la réponse
  • Session partagée : en production, le bot partage la même session Playwright que l'agent d'envoi (auto_sync.py)

⚙️ Défis Techniques Résolus

  • Squash push Git : git commit-tree master^{tree} -p FETCH_HEAD contourne le rejet des fichiers >10 MB (cache WhatsApp wa_session/)
  • Module cache Python : auto_sync.py doit être redémarré pour charger un nouveau reconciliation_global.py modifié
  • Doublons MSISDN dans OOS : groupby + mean() pour numériques, first() pour catégoriels
  • Day_Target vs OOS_Target : Day_Target est 9.6× plus grand que OOS_Target — utiliser le mauvais dénominateur produit des jours de stock artificiellement faux
  • Sélecteurs WhatsApp : WhatsApp Web change ses attributs HTML fréquemment — stratégie multi-sélecteurs avec fallback
  • balance_history.csv : retiré du tracking Git (git rm --cached) pour éviter l'écrasement de l'historique HF par les squash pushs

📈 Métriques du Tableau de Bord

  • Taux OOS : % agents dont Balance < Montants OOS (cible rupture)
  • Taux Rupture : % agents dont Jours de Stock < 0.7 (seuil 70%)
  • Injection nécessaire : Σ |Valeur Calculée| pour les agents en rupture (FCFA)
  • Jours de Stock : Balance ÷ Day_Target (couverture en jours)
  • Récidivistes : agents en rupture sur ≥ 2 cycles consécutifs
  • Nouveaux POS actifs : agents dans cycle_history qui ont une transaction dans summary.xlsx
  • Tendance journalière : évolution du taux rupture global cycle par cycle (intra-day)
